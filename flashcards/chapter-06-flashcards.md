## Chapter 6: BigQuery Storage Optimization — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | Max number of partitions allowed per BigQuery table? | 4,000 partitions per table. Exceeding this on DML/load fails. Exam tip: if a scenario needs more granularity than 4,000 partitions allow, consider clustering in addition to (or instead of) further partitioning. |
| 2 | Max number of clustering columns per BigQuery table? | 4 columns. Order matters — the first clustering column has the greatest pruning/sort benefit. Exam tip: put the most selective/frequently filtered column first. |
| 3 | Default BigQuery time travel window, and min/max configurable range? | Default: 7 days. Configurable range: 2–7 days (set via dataset max_time_travel_hours). Exam tip: lowering the window reduces storage cost of retained deleted/changed data. |
| 4 | On-demand BigQuery query pricing model? | Billed per TiB of data scanned (~$6.25/TiB), with 1 TiB/month free. No reservation needed. Exam tip: best for unpredictable/low-average workloads. |
| 5 | When should you choose flat-rate / Editions (slot-based) pricing over on-demand? | When query volume is high, steady, and predictable — reserved slots amortize cost better than per-byte billing at scale. Exam tip: high, consistent utilization → editions/slots; bursty/unpredictable → on-demand. |
| 6 | BigQuery storage pricing: active vs long-term storage? | Active storage: modified within the last 90 days, higher rate (~$0.02/GB/month). Long-term storage: table/partition untouched 90+ consecutive days, automatically discounted (~$0.01/GB/month). Exam tip: no action needed — the discount applies automatically per partition. |
| 7 | Partitioning vs Clustering — core distinction? | Partitioning: splits table into separate segments prunable via metadata (max 4,000, one column/expression, DATE/TIMESTAMP/DATETIME/INTEGER-range). Clustering: sorts rows within storage blocks for up to 4 columns, better for higher-cardinality filter/sort/aggregate columns. Exam tip: use both together — partition first, cluster second. |
| 8 | Materialized View vs Scheduled Query — when to use which? | Materialized View: automatic incremental refresh + automatic query rewrite by the optimizer, low latency for repeated aggregation patterns. Scheduled Query: full re-run on a cron schedule, no automatic rewrite, more flexible arbitrary SQL/DDL. Exam tip: near-real-time dashboards & auto-optimization → materialized view; complex one-off ETL/transform jobs → scheduled query. |
| 9 | Three BigQuery partitioning strategies? | 1) Time-unit partitioning (DATE/TIMESTAMP/DATETIME column, granularity HOUR/DAY/MONTH/YEAR) 2) Ingestion-time partitioning (uses pseudo-columns _PARTITIONTIME/_PARTITIONDATE) 3) Integer-range partitioning (start, end, interval on an INTEGER column). Exam tip: choose integer-range for numeric IDs, not time-unit. |
| 10 | SQL syntax to partition and cluster a table at creation? | CREATE TABLE ds.tbl (col1 DATE, col2 STRING) PARTITION BY col1 CLUSTER BY col2; Exam tip: PARTITION BY takes exactly one column/expression; CLUSTER BY can list up to 4, most-selective first. |
| 11 | SQL syntax to create a materialized view? | CREATE MATERIALIZED VIEW ds.mv_name AS SELECT ... FROM ds.base_table GROUP BY ...; Exam tip: only certain SQL patterns (aggregations like SUM/COUNT/AVG, some joins) are supported for auto-refresh/rewrite — not arbitrary SQL. |
| 12 | Cost optimization pattern: table scanned frequently by date, rarely older than 6 months? | Partition by DATE, cluster on frequent filter columns, and rely on automatic long-term storage discount for partitions >90 days untouched; optionally set table/partition expiration to auto-delete stale data. Exam tip: this combo (partition + cluster + expiration) is a classic exam 'best answer' pattern. |
